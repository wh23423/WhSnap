## 二、按键设计评估

### 2.1 做得对的地方（先说好的，避免误伤）

| 设计 | 证据 | 价值 |
|---|---|---|
| **四层作用域分离**（Global / Overlay / Pin / Annotation） | `hotkey` 目录 `HotkeyScope` 枚举 | 遮罩里的 `Enter` 不会和别的软件抢键，这是冲突检测能出正确结论的前提 |
| **单一数据源 + 全部可配置** | `HotkeyCatalog.All` 是全表唯一来源；所有按键统一走 `HotkeyBindings.Resolve/Match`（标注 `AnnotationWindow.xaml.cs:1007`、贴图 `PinWindow.cs:585`） | 没有"某些键藏在代码里改不了"的分裂 |
| **键帽文案读用户绑定而非写死** | `OverlayWindow.xaml.cs:163-173`（`_session.KeyText(...)`）、`OnboardingWindow.xaml.cs:264` | 改键后界面跟着变（但见 3.1 的例外） |
| **局部按键与文字输入互不干扰** | `AnnotationWindow.xaml.cs:1001-1005`：就地编辑文字时直接放行给输入框 | 输入 "R" 不会切成矩形工具，这个坑避掉了 |
| **默认避开误触** | `pin.closeAll`（关闭全部）与 `pin.showPanel` 默认**不绑定**（`HotkeyCatalog.cs:41-44`） | 破坏性动作不占键，判断正确 |
| **热键注册失败不静默** | `App.xaml.cs:281-285`：冲突时弹气泡并指向改键入口 | 符合"绝不静默失败" |

### 2.2 问题清单（按影响排序）

> **修订说明**：本节经两轮独立复核后**修正了 3 处原始判断错误**并**新增 1 个 P0 缺陷**。
> 被推翻的原判断集中列在 §2.3「本报告的更正记录」，以免误读。

#### 🔴 P0-1　全局 `F1` 与系统"帮助"键对撞，且冲突源库自相矛盾　【✅ 已修：`bd3705e`】
- 现状：`capture.region` 默认 `F1`（`HotkeyCatalog.cs:35`），是**全局热键**，
  启动时经 `HotkeyManager` 注册、**捕获期间从不释放**（注册集中在 `App.xaml.cs:372` 启动与
  `HotkeyManager.cs:289` 唤醒回调，全库无低层键盘钩子可绕过）。
- 为什么严重：`RegisterHotKey` 是**系统级独占**。注册成功后，前台程序**再也收不到 `F1`**
  （资源管理器/Word/浏览器的"帮助"直接失效），而用户按 F1 会莫名其妙多一张截图。
  且 `HotkeySpec.cs:19` 的 `RegisterModifiers` 不强制要求修饰键，所以"单功能键占全局"在这套实现里是允许的。
- **自相矛盾的证据**：`HotkeyConflict.cs:39` 在给 `PrtScn` 的建议里写着
  **"关掉该开关，或换用 F1 之类的自定义键"**——主动推荐 F1；而同一个文件 `:52` 又把
  `F1` 登记为 **"Snipaste / 各类帮助键"** 冲突源。**建议与告警互相打架**，必须改掉一处。
- 建议：默认改为 `Ctrl+Alt+A`（微信/QQ 系用户熟悉，且不与帮助键冲突），
  `F1` 作为可选第二绑定；同时把 `:39` 那条建议改成不推荐 F1。
  迁移要点：`SettingsService.cs:242` 有"旧默认值自动迁移"判断（当前判 `F1`），改默认键必须同步。
- 附带：`capture.pinClipboard` 默认 `F3`（`HotkeyCatalog.cs:37`）同属"常用单功能键被全局独占"
  （浏览器/IDE 的 F3=查找下一个会失效），建议一并改成带修饰键的组合。

#### 🔴 P0-2【新发现，比原判断更严重】全局 `F3` 把遮罩内的同名快捷键"吃掉"了　【✅ 已修：`bd3705e`】
- 现状：全局 `F3` = `capture.pinClipboard`（`HotkeyCatalog.cs:37`）；遮罩内 `F3` = `overlay.pin`
  （`:57`，语义是"选区直接贴图"）。遮罩的**提示条还会显示"F3 贴图"**（`OverlayWindow.xaml:211-213`，
  键帽值取自 `overlay.pin`）。
- **为什么这是真缺陷**：跨作用域撞键**不参与冲突检测**——`HotkeyConflict.cs:142` 按作用域分组，
  其超类注释 `:127` 明说"跨作用域不算冲突"。于是两处都绑了 `F3` 却互不告警。
  而捕获时全局注册**仍然生效**、并不释放，按 `F3` 会被系统投递 `WM_HOTKEY` 走**全局**动作
  （把剪贴板内容贴成新图），`OverlayWindow.xaml.cs:223` → `OverlaySession.cs:471-476` 里那条
  `overlay.pin` 分支**根本收不到按键**。
- **后果**：遮罩提示条承诺"F3 贴图（贴当前选区）"，用户按下去却去贴了**剪贴板里的旧内容**。
  这是"提示与实际行为不一致"里最伤信任的一类。
- 诚实边界：该结论由代码路径推出（全局注册不释放 + 跨作用域不检测 + 提示条显示该键），
  **尚未在真机按下 F3 复验**。但三处代码证据一致，且修复方向无论真机结果如何都成立。
- 建议：
  1. **补跨作用域检测**：Global 与 Overlay（及 Pin/Annotation）之间同名键必须告警或禁止配置；
  2. **让"局部优先"成为真规则**：进入遮罩时临时注销与遮罩冲突的全局热键，退出时恢复；
  3. 最小改动：遮罩内"直接贴图"改为不冲突的键（如 `Shift+Enter`）。

#### 🔴 P0-4　`T` 键一键三义
- `overlay.annotate`（`HotkeyCatalog.cs:59`）/ `annotation.tool.text`（`:85`）/ `pin.thumbnail`（`:101`）

- 为什么绊人：贴图与标注是**连续使用**的流程（贴图 → 空格进标注 → 选工具）。
  用户刚在贴图上按 `T` 切了缩略图，进标注后按 `T` 以为是缩略图，结果切成了文字工具。
- 建议：`pin.thumbnail` 改为不与标注/遮罩冲突的键（如 `Shift+T` 或 `Ctrl+T`），
  并在跨作用域检测里覆盖这类"局部 vs 局部"的组合。

沿用现有 `--selftest` / `--settings-test` 的写法。**关键前提（本轮核实）**：
现有 `--pin-test`/`--annotate-test` 是**直接调逻辑方法**（`PinTestCommand.cs:131,148,203`、
`AnnotationTestCommand.cs:397`），`--overlay-test` 虽调 `HandleKey`（`OverlayTestCommand.cs:225,261`）
但**绕过真实键盘事件**。更值得注意的是，M7 新增的 `--focal-test` 已经能给**设计一致性**加上
6 条断言（令牌齐全、度量一致、图标可解析、对比度红线、界面无字面量色值、`FocalTestCommand.cs:142-308`），
却**没有任何一条断言关心"按键是否真的通到动作"**——所以 `P0-2` 这类"全局抢占局部键"的 bug

1. **可达性（真按键）**：对 `HotkeyCatalog.All` 中每个有默认键的动作，按其作用域**真实派发按键**
   （参考 `PowerTestCommand.cs:226` 投递 `WM_HOTKEY` 的做法），断言目标动作被触发；
2. **无写死**：把 `capture.region`、`capture.pinClipboard`、`annotation.undo` 改成非默认值后，
   **遍历所有用户可见字符串**（启动气泡、引导 Hero 与自启动说明、设置说明、贴图右键菜单、
   标注 ToolTip 与速查条、贴图面板空状态），断言不含旧键名——一次性锁死 P0-3 的全部 8 处；
3. **无跨作用域抢占**：断言"全局已注册的键"不会同时被某个局部作用域绑定；若绑定，检测必须报冲突——

4. **无复义**：`T` 不再同时出现在 `overlay` / `annotation.tool` / `pin` 三个作用域；
5. **文案数值一致**：颜色历史面板显示的容量 == `SettingsSchema` 的 `ColorHistoryRetention` 取值；
6. **引导一致**：`OnboardingWindow` Hero 文本包含 `KeyText("capture.region")` 的当前值；
7. **破坏性动作安全**：`pin.closeAll` 等默认不绑定（已有约束，加断言固化）。

## 五、结论与建议顺序

1. **可直接交付**：功能与发布链路已闭环（`v1.0.0-preview.2` 签名版在线），质量门禁全绿。
2. **但在给身边人用之前，建议先做阶段一**，理由按杀伤力排序：
   - **P0-2（全局 `F3` 吃掉遮罩内 `F3`）**：提示条写着"F3 贴图"，按下去却贴了剪贴板旧内容——
     "承诺的功能不工作"，最伤信任；
   - **P0-3（8 处硬编码键名）**：改键后提示开始说谎，用户越改越乱；
   - **P0-4（`T` 一键三义）**：连续操作时会切错工具；
   - **P0-1（`F1` 占帮助键）**：影响范围延伸到整个系统，且冲突源库自己都在推荐 F1。
3. **需要你拍板的两件事**：
   - `F1` 是否改为 `Ctrl+Alt+A`（更稳 vs 改变你的肌肉记忆）；
   - "局部优先"的实现方式：进遮罩时**临时注销**冲突的全局热键（更贴合用户直觉），
     还是把遮罩内 `F3` 改成别的键（改动更小、风险更低）。
4. **一个被低估的亮点 + 一个结构性盲点**：热键冲突的呈现（红色徽标 + 顶部横幅 + 一键改绑 +
   `block`/`save-disabled` 两种策略）已比多数同类工具好，投入没白费；唯一缺口是"被系统占用时
   说不出是谁占的"。但它有个**结构性盲点**——跨作用域撞键被 `HotkeyConflict.cs:142` 放过，
   所以最危险的那类冲突恰好检测不到。这也解释了 P0-2 为什么能活到今天。
5. **现有自检抓不到这类问题**：`--pin-test`/`--annotate-test` 直接调逻辑方法、
   `--overlay-test` 绕过真实键盘事件；而 M7 的 `--focal-test` 已经能对**设计一致性**下 6 条断言。
   也就是说**视觉一致性有护栏、按键可达性 0 条**——这个不对称正是 P0-2/P0-4 能活到今天的原因。
   建议与阶段一同时落地 `--ux-test`（§4），把这次发现的问题转成不会复发的护栏。
